# Release Skill

Derive a GitHub release's title and body from a `CHANGELOG.md` section, then create or re-sync the git tag and GitHub release to match. This is the single owner of skein's release-note shape — before this skill existed, every release was a hand-typed `gh release create --notes "..."` call, and skein's own 11 releases drifted into three visibly different shapes as a result (see `docs/dev_plans/20260712-feature-release-skill.md`).

This skill is **user-invoked only** (`disable-model-invocation: true`): it pushes a git tag and publishes a public GitHub release — an externally-visible, hard-to-reverse action — and must never fire off conversational context alone.

## Usage

- `/release 0.6.0` — cut or re-sync the release for `CHANGELOG.md`'s `## [0.6.0]` section (**Single-Version Mode**, Steps 1–6)
- `/release latest` / `/release unreleased` — same, targeting the topmost dated section in `CHANGELOG.md` (skipping any `## [Unreleased]` heading, which has no release yet)
- `/release` with no argument — same as `latest`
- `/release audit` — scan every tag and CHANGELOG version for gaps or drift and report a punch list; does not mutate anything by itself (**Audit Mode**, below)

## Canonical Format

- **Title**: `<repo> vX.Y.Z — <highlight>`. `<repo>` is the bare repository name — take it from the `name` field Step 2 item 4 already fetched and cached (`gh repo view --repo ORIGIN_REPO --json name,nameWithOwner`, passed `--repo` explicitly) so the result cannot be redirected by a `GH_REPO`/`GH_HOST` environment override — do not call `gh repo view` without `--repo`, and do not parse `git remote get-url origin` directly for this either: that returns a full remote URL (e.g. `git@github.com:owner/repo.git` or `https://github.com/owner/repo.git`), not a bare name, so literal use produces a malformed title. `<highlight>` is a short (under ~60 chars) one-line summary of the version's single biggest change — **you must draft this yourself by reading the section body**; do not attempt to mechanically extract it from bullet text (a title-cased first bullet reads as noise, not a summary).
- **Body**, in order:
  1. **`## What's New`** (optional but the default — omit only if the user asks for a bare CHANGELOG-only body) — a short (2–4 sentence) prose paragraph, drafted fresh by you from the section body, giving a reader who won't parse bullet points the shape of the release before they hit the itemized list. Not a bullet-point restatement — say what changed and why it matters, the way a human release-note author would frame it. This is the same kind of judgment call as `<highlight>` (Step 3), just longer.
  2. The CHANGELOG section's content *below* its `## [X.Y.Z] - date` header — the `### Added`/`### Changed`/`### Fixed`/etc. subsections verbatim, header stripped (GitHub already shows the tag and date).
  3. A blank line, then:
     ```
     **Full diff:** https://<HOST>/<owner>/<repo>/compare/vPREV...vNEW
     ```
     `<owner>/<repo>` here is `ORIGIN_REPO` itself (Step 2), taken from the `nameWithOwner` value Step 2 item 4 already fetched and cached — do not hand-assemble it from a parsed remote URL, for the same reason as the title's `<repo>`, and do not issue a fresh `gh repo view` for it. `<HOST>` is ORIGIN_REPO's host segment (the `HOST` of the `HOST/OWNER/REPO` triple Step 2 parsed), used literally instead of a hardcoded `github.com` — so a GHE / non-github.com origin gets a live compare link on its own host rather than a dead public-github.com one. Omit this line entirely when there is no PREV tag (the first-ever release).

`<repo>`/`<owner>` derived this way are safe to interpolate directly: GitHub repository and owner names are restricted to alphanumerics, hyphens, underscores, and periods — they cannot carry shell metacharacters or quote characters the way CHANGELOG-derived body/highlight text can (see Step 6).

## Single-Version Mode

### Step 1: Resolve the Target Version and Section

1. Read `CHANGELOG.md`. Find the target `## [X.Y.Z] - date` header:
   - Explicit `X.Y.Z` argument → match that exact version.
   - `latest`/`unreleased`/no argument → the topmost `## [X.Y.Z] - date` header (skip any leading `## [Unreleased]` heading — it has no date and no release yet; if the file has no dated section at all, stop and tell the user).
2. **Validate the resolved version string against strict SemVer (`^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` — each component rejects a leading zero, e.g. `01.2.3`, per SemVer's own numeric-identifier rule) before it is used anywhere else in this skill.** Every later step splices this string, unquoted, into `git`/`gh` commands (`vX.Y.Z` tag names, `gh release view vX.Y.Z`, etc.) — an unvalidated value (a malformed explicit argument, or a CHANGELOG header with drifted/malicious punctuation matched via the whitespace-tolerant retry in Step 1 item 5 below) could otherwise carry shell metacharacters into those commands. If the resolved version fails this check, stop and report the exact string rather than passing it on.
3. Extract everything between that header and the next `## [` header (or EOF). Strip the header line itself and any leading/trailing blank lines. This is the raw body.
4. If the target section is empty (a version bump with no recorded changes), stop and tell the user — do not publish an empty-body release silently.
5. If no header matches exactly, retry tolerating whitespace/punctuation drift (extra spaces, en dash vs. hyphen) before giving up — this is a cross-skill format contract shared with `skein:update-docs` (see Execution Model below), and CHANGELOG.md is hand-edited, so minor formatting drift is expected. If still no match, stop and report the exact version string you searched for rather than guessing at loosely-matched boundaries. Any tolerantly-matched result still passes through step 2's SemVer validation before use.

### Step 2: Determine the Previous Version and Lock the Target Repository

Before running any `gh` command, resolve the host-qualified owner/repo from the same remote that Step 5 pushes the tag to, and lock every subsequent `gh` call to it. `gh`'s implicit repo resolution can be redirected by a `GH_REPO`/`GH_HOST` environment override (or ambient config) independent of what `git push origin` actually targets — without this, the tag could be pushed to repository A while the release is created/edited in repository B, with the confirmation in Step 4 never having surfaced the mismatch:

1. Resolve the remote from the URL Step 5 actually pushes to, and confirm the fetch URL agrees. Run both `git remote get-url origin` (fetch) and `git remote get-url --push --all origin` (push) — note `--all`: a remote may have **multiple** `pushurl` entries and a plain `git push origin <tag>` pushes to **every** one of them, so a single-URL read (`get-url --push` without `--all`) would validate only the first while the tag lands on all. Require the push side to resolve to exactly one `HOST/OWNER/REPO` (stop and report if `--all` returns more than one distinct triple), and confirm the fetch URL resolves to that same host/owner/repo — if any diverge (e.g. a second `remote.origin.pushurl` points at a different endpoint), stop and report every URL rather than silently picking one — redact any embedded userinfo — the two-part `user:token@`/`user:pass@` shape and the equally common bare single-token shape with no `user:` prefix (e.g. `ghp_abc123@github.com`) from each URL before displaying it, so a credential embedded in a remote URL is never echoed into the session — since ORIGIN_REPO would otherwise be resolved against a different endpoint than the tag is pushed to. Parse the **fully-qualified** `HOST/OWNER/REPO` triple from the (single) push URL (strip a trailing `.git`, drop any `ssh://` port, and strip any embedded userinfo — both the two-part `user:token@`/`user:pass@` shape and the equally common bare single-token shape with no `user:` prefix (e.g. `ghp_abc123@github.com`) — before use: `git@github.com:owner/repo.git` → `github.com/owner/repo`, `https://github.com/owner/repo.git` → `github.com/owner/repo`, `ssh://git@ghe.example.com/owner/repo.git` → `ghe.example.com/owner/repo`, `ssh://git@ghe.example.com:2222/owner/repo.git` → `ghe.example.com/owner/repo` with the port dropped). Call this origin-authoritative, host-qualified triple `ORIGIN_REPO`. Keep the host: a bare `owner/repo` passed to `--repo` still lets a poisoned `GH_HOST` redirect `gh` to a different host than the git remote, whereas a host-qualified `--repo` value pins the host and is immune to `GH_HOST`.
2. **Validate `ORIGIN_REPO` against GitHub's host/owner/repo naming charset (`^[A-Za-z0-9]([A-Za-z0-9.-]*[A-Za-z0-9])?/[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$` — the host segment forbids a leading/trailing `-`/`.` so an argument-injection shape like `-evil.com/owner/repo` cannot slip through) before its first use.** It comes from `.git/config`, which is not GitHub-validated content and is spliced into every `gh --repo …` call, so it gets the same gate the version token gets in Step 1.2. On mismatch, stop and report the exact string — first redacting any embedded userinfo from it (the two-part `user:token@`/`user:pass@` shape and the equally common bare single-token shape with no `user:` prefix, e.g. `ghp_abc123@github.com`), in case an unanticipated URL shape or code path still left a credential embedded in `ORIGIN_REPO` at validation time — rather than passing it on.
3. From here on, pass `--repo ORIGIN_REPO` explicitly to **every** `gh` command this skill runs — `gh repo view`, `gh release view`, `gh release create`, `gh release edit`, `gh release list` — never rely on `gh`'s ambient resolution again. A host-qualified `--repo` value takes precedence over `GH_REPO`/`GH_HOST`, so this closes the redirection risk directly rather than merely detecting it after the fact.
4. As a sanity check, run `gh repo view --repo ORIGIN_REPO --json name,nameWithOwner,defaultBranchRef` once now and confirm the `nameWithOwner` `owner/repo` it echoes matches the owner/repo portion of `ORIGIN_REPO` (the `nameWithOwner` field carries no host, so compare the owner/repo tail, not the full host-qualified triple) — if it errors (repo doesn't exist, `gh` isn't authenticated for it), stop and report rather than continuing on an unresolved repo. Fetch **`name`, `nameWithOwner`, and `defaultBranchRef`** in this one call and cache them: Canonical Format's title uses the bare `name`, its `**Full diff:**` compare link uses the `nameWithOwner` `<owner>/<repo>` pair, and Step 4's New-tag case uses `defaultBranchRef.name` to flag a release cut from a non-default branch — so this single `--repo`-scoped call covers all three derivations, and no second `gh repo view` (scoped or unscoped) should be issued later.
5. **A `git fetch`/`git ls-remote` call against `origin` that fails for a transport, auth, or permission reason must stop the skill and report the exact error — never be treated as "origin has no such tag."** Before reporting, redact any embedded userinfo — the two-part `user:token@`/`user:pass@` shape and the equally common bare single-token shape with no `user:` prefix (e.g. `ghp_abc123@github.com`) from a remote URL that appears in that error text — `git`'s own auth-failure messages routinely echo the URL verbatim, and a credential must never be echoed into the session on a failure path. This applies to every origin read in this skill (here, Step 4's tag-existence check, Audit Step A1's tag inventory). `git ls-remote --exit-code` specifically returns exit code **2** for a confirmed empty match — that, and only that, is safe to read as legitimate absence. Any other nonzero exit (DNS failure, SSH auth failure, timeout, a plain `git ls-remote`/`git fetch` erroring with no `--exit-code` to disambiguate) is inconclusive and must not silently fall through to a "tag is new" or "first-ever release" code path — a transient network blip could otherwise cause a re-sync to be misread as a brand-new release.

**This pre-confirmation path never fetches or mutates local tags — no `git fetch` runs here at all.** An earlier revision ran `git fetch --tags --force origin` at this point to reconcile a local tag list before deriving PREV from it, but that force-fetch silently moved **every** local tag that also existed on origin (not just the target `vX.Y.Z`) to match origin's position — an unannounced mutation during what is supposed to be a read/preflight phase, one that would fire the instant the fetch ran and so could destroy an operator's intentional local tag divergence even on a run that then aborts immediately afterward for an unrelated reason (an ambiguous `gh release view` failure in Step 3.1, say). That fetch is now removed entirely, because its only two justifications are both served without it: PREV is derived directly from an origin-authoritative `git ls-remote --tags origin` read (below), so no local tag list needs reconciling for PREV purposes; and the target tag's origin-authoritative state is read from that same `ls-remote` snapshot in Step 4, so nothing downstream needs a freshly-fetched **local** copy of `vX.Y.Z` either (Step 4's local reads are used only to detect a local-only target tag and to disclose local-vs-origin divergence — never as a stand-in for origin truth). Leaving local tags untouched is what preserves the local-only-tag recovery path Step 4/5 depend on: a local-only tag from a prior interrupted run survives here simply because this path never fetches at all — the stronger guarantee that the old "fetch but never `--prune`/`--prune-tags`" rule was reaching for, since a fetch that never runs can neither prune a local-only tag nor force-move a diverged one. The accepted tradeoff is that a tag deleted on origin, or a local tag the operator force-moved, can linger in this clone's local list at a stale position — but every origin-authoritative decision in this skill (PREV membership, Step 4's tag-existence classification, Step 6's TOCTOU re-verify) reads origin directly via `git ls-remote` and never trusts the local list for it, and Audit Mode's classification (Step A2) likewise treats a locally-only-known tag as at most an informational finding, never as something it silently trusts as `ok`.

Then build the PREV candidate list **directly from the origin-authoritative tag inventory** — never from local `git tag --list`. Run `git ls-remote --tags origin` (if this call fails outright rather than returning an empty-but-successful list, that is a transport/auth failure per item 5 above — stop and report, do not treat it as "origin has zero tags"). From each returned ref, strip the `refs/tags/` prefix and any trailing `^{}` dereference marker to recover the bare tag name, then keep only names matching the strict-SemVer shape `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` (this excludes both non-release tags — e.g. `nightly`, `release-2020` — and malformed/prerelease version-shaped tags — e.g. `v1.2`, `vfoo`, `v1.2.3-beta`, `v01.2.3` — any of which would otherwise enter semver-sort ordering with implementation-defined or unintended placement and could get picked as a garbage PREV), and sort the survivors by semver order (`v:refname` / `sort -V`). Sourcing PREV straight from origin — rather than from a local list reconciled by a fetch — is precisely what lets this path drop the force-fetch: a tag that exists only in this clone's local list (deleted on origin, or a locally created test tag) never enters the candidate set in the first place, so it can never be selected as a stale PREV that would produce a broken `**Full diff:**` compare link — and Audit Mode's `ok`/`drifted` check (Step A2), which resolves PREV by this same origin-sourced rule, is protected from the same misclassification. **This origin-only derivation governs PREV selection alone — it does not govern Step 4's local-only *target*-tag detection**, which deliberately consults the local tag list (via `git rev-parse`) to recover and push a deliberately-retained local-only tag (a distinct, intentionally-preserved use case that this rule must not weaken). Take this `ls-remote` snapshot **before** any new tag this run might create (tag creation happens in Step 5, not here — origin cannot yet carry a tag this same run is about to push). Exclude the target version's own tag `vX.Y.Z` from the list if present (the re-sync case, where the tag already exists on origin) — PREV must never resolve to the target version itself. From what remains, PREV is the highest tag by semver order that sorts below `vX.Y.Z`. **Once PREV is selected, record its peeled commit SHA from that same `git ls-remote` output** — the SHA on PREV's `refs/tags/vPREV^{}` peeled line (the full 40-char commit SHA; a pre-existing lightweight PREV tag has only the bare `refs/tags/vPREV` line, whose SHA is itself the commit) — **and carry it forward** (do not `git rev-parse` PREV locally, since this path never fetched and the local `vPREV` ref may be stale or absent — origin is the source of truth here). Step 6 re-verifies PREV's remote tag against this exact value immediately before publishing, the same way Step 4 records the target tag's SHA for Step 6's target-tag re-verify, so a concurrent force-move or deletion of PREV between here and publish cannot silently ship a stale or dead `**Full diff:**` compare link. Tags are the canonical ordering source, not CHANGELOG section order, because the two can disagree in either direction: a CHANGELOG section can be written before its tag is pushed, and an old tag can predate CHANGELOG coverage entirely (skein's own `v0.2.x`/`v0.1.0` had no changelog-derived notes at release time). If no such tag exists after excluding the target, this is the first-ever release — omit the compare line (Step 3).

**Worked example (re-sync case):** target `v0.5.1`, origin-sourced (`git ls-remote --tags origin`) sorted tag list `v0.1.0 v0.2.0 v0.2.1 v0.2.2 v0.2.3 v0.2.4 v0.3.0 v0.4.0 v0.4.1 v0.5.0 v0.5.1`. Exclude `v0.5.1` itself → PREV is `v0.5.0`, the entry immediately before it in sorted order.

### Step 3: Compose Title and Body

1. Run `gh release view vX.Y.Z --repo ORIGIN_REPO --json name,body,isDraft,isPrerelease` once, now — this single call also serves as the release-existence check Step 6 acts on later, so Step 6 must reuse its outcome rather than re-querying. Distinguish confirmed absence from any other failure — do not treat every non-zero exit as "no release yet":
   - If it fails with stderr exactly `release not found`, no release exists yet (new-release case). Record this outcome for Step 6, and draft the title and `## What's New` paragraph yourself from the extracted section body (Step 1) — the version's single biggest change for the highlight, a short synthesis paragraph for What's New.
   - If it fails with any other message (auth failure, network error, repo-resolution error, insufficient permissions), **stop and report the exact error now** — do not proceed to compose a release on an ambiguous failure, and do not let Step 6 fall through to `gh release create`.
   - If it succeeds (release already exists — the re-sync case), record this outcome for Step 6, **including the fetched `isDraft`/`isPrerelease` values — this is the baseline Step 6's edit-path re-verify compares against.** `gh release view --json` exposes the release title as the field **`name`**, not `title` (`title` is only a flag on `gh release create`/`edit`, never a JSON output field; verify with `gh release view --help` if in doubt). Try to recover the existing highlight from `name` (the text after the em dash) and the existing `## What's New` paragraph from the body (the prose block between the `## What's New` heading and whichever comes first of: the next `###` heading, the next `##` heading, the `**Full diff:**` line, or EOF — a body with no trailing subsections has no `###` to terminate on, and the boundary must not silently swallow the CHANGELOG content or compare link that follows). Propose reusing both rather than re-drafting from scratch — this is what makes re-sync reproducible in practice, since neither has any other persisted source of truth. If the existing title doesn't match the `vX.Y.Z — <highlight>` shape, or the body has no `## What's New` section, draft whichever piece is missing yourself instead of recovering it. **Additionally, if the recorded `isDraft` or `isPrerelease` is `true`, the existing release is currently a draft or a prerelease — not a published stable release — and Single-Version Mode is about to edit it as though it were an ordinary stable re-sync (`gh release edit` in Step 6 is neither draft- nor prerelease-aware and will neither promote, demote, nor publish it). This is *not* a hard block — a direct `/release X.Y.Z` invocation may legitimately intend to edit a draft's or prerelease's notes — but it must never happen silently: surface the draft/prerelease state prominently and explicitly in Step 4's confirmation (not buried in the body diff), state plainly that the release is currently a draft/prerelease rather than a published stable release, and require the user to specifically acknowledge editing it in that state (not a generic "yes, cut the release") before Step 6 proceeds — the same acknowledgment discipline the Local-only-tag, branch-mismatch, and divergent-target-tag cases use for their own ambiguity. Audit Mode has explicit `drafted`/`prereleased` early-exit classifications for exactly this situation; Single-Version Mode has no such early exit, so this Step 4 acknowledgment is its equivalent safeguard.**
   - Either way, state title and What's New to the user as part of the confirmation in Step 4 and let them override either one. The CHANGELOG-derived body content and compare link are fully deterministic and reproducible on their own; the **title** and the **What's New paragraph** are only reproducible when recovered or re-supplied identically — they're both fresh judgment calls, not derived state.
2. Compose the title: `<repo> vX.Y.Z — <highlight>`.
3. Compose the body per the Canonical Format order: the `## What's New` paragraph (unless the user asked for a bare body), then the Step 1 section content, then (if a PREV tag exists) a blank line and `**Full diff:** https://<HOST>/<owner>/<repo>/compare/vPREV...vNEW` (`<HOST>` = ORIGIN_REPO's host segment from Step 2, not a literal `github.com`).
4. **Record the confirmed payload snapshot.** Once the title, highlight, `## What's New` paragraph (if included), and body are fully composed, compute a content snapshot — a hash (e.g. SHA-256) of the concatenation, in this fixed order, of: the raw bytes of the CHANGELOG section extracted in Step 1 item 3 (the section body exactly as extracted there, before any further composition), the composed title (`<repo> vX.Y.Z — <highlight>`), the highlight text on its own, and the composed `## What's New` paragraph (an empty string if the user asked for a bare body). Call this the **confirmed payload snapshot**. Record it alongside the actual composed title/body strings themselves, and carry all of it forward *literally* into Steps 5 and 6 — the same way Step 4 below carries the confirmed commit SHA forward as a pinned value rather than re-deriving it later. Steps 5 and 6 write the tag message and release notes from this literal, already-composed content; a fresh `CHANGELOG.md` read is used only for the *comparison* in Step 5/Step 6's re-verify (below), never as an alternate publish source — so a run that passes the re-verify never ends up publishing a second, independently re-derived version of the same content that might disagree with what the user actually saw. **Explicitly excluded** from this snapshot: the resolved commit SHA, `ORIGIN_REPO`, PREV's SHA, and the release's `isDraft`/`isPrerelease` state — each of those already has its own dedicated re-verify mechanism (Step 6's tag-SHA re-verify, PREV re-verify, and release-object re-verify respectively), and folding them in here would blur what a mismatch in *this* snapshot actually means: a change to the CHANGELOG-derived content itself, nothing else. This snapshot — not some looser notion of "the release" — is exactly what Step 4 shows the user and what Step 4's confirmation approves.

### Step 4: Confirm Before Mutating

First determine whether this run will create a brand-new tag or reuse an existing one — this changes what "the intended commit" means and must not be conflated:

- Check tag existence in two places: **local** via `git rev-parse --verify --quiet "refs/tags/vX.Y.Z"`, and **origin** by looking up `vX.Y.Z` in the origin tag-name set Step 2 already captured (the `git ls-remote --tags origin` snapshot it built as the PREV candidate source — reuse it rather than issuing a second `git ls-remote` for this single ref). That snapshot already carries Step 2 item 5's fail-closed guarantee: a transport/auth failure on Step 2's `ls-remote` already stopped the run before reaching here, so a `vX.Y.Z`-absent-from-the-set result here is a *confirmed* absence, never a masked read failure. The **origin** read is origin-authoritative because it comes from that live `git ls-remote --tags origin` snapshot; the **local** read reflects only this clone's own tag refs, which this path never fetched or reconciled — and that separation is deliberate, because it is exactly what distinguishes the three cases below (a tag on origin but not local, or local but not on origin, is a meaningful classification, not a discrepancy to paper over). Do not re-`ls-remote` and do not fetch here, but do not skip Step 2 either (Single-Version Mode always runs Steps 1–6 in order). (Step 6's TOCTOU re-verify is a deliberately *separate*, fresh origin read — do not fold it into this reused snapshot, since the Step 4 confirmation gate time-separates the two and a force-move can land in between.) Record which of the three cases below applies — Step 5 reuses this determination rather than re-checking.
- **New tag** (found in neither place): run `git status --porcelain` and stop if the worktree is dirty — uncommitted changes make it ambiguous whether `HEAD` is actually the commit the user intends to release, and a tag/release is hard to undo once pushed. Then run `git rev-parse --abbrev-ref HEAD` and `git rev-parse HEAD` to record the current branch and **commit SHA** that Step 5 will tag — Step 5 passes this exact SHA to `git tag` explicitly, so nothing that happens to `HEAD` between this confirmation and Step 5 (a concurrent commit, a checkout) can change what actually gets tagged. **Compare the recorded branch against Step 2 item 4's cached `defaultBranchRef.name`** — GitHub returns `defaultBranchRef: null` for a repository with no commits/branches yet or a deleted default branch ref, so check for `null` first and skip this comparison entirely in that case (there is no default branch to compare against, and this is not itself a mismatch). Otherwise, if the branches differ, this release is being cut from a non-default branch (e.g. an unmerged feature branch rather than the repo's normal integration branch); state this explicitly in the confirmation below and require the user to affirmatively acknowledge cutting a release from that specific branch (not a generic "yes, cut the release") before proceeding, the same acknowledgment discipline the Local-only-tag case uses for its own ambiguity — a clean worktree alone says nothing about whether `HEAD`'s branch has actually been merged. **If you reached this branch fixing an *older* `missing-tag` version surfaced by `/release audit` — an Audit Step A4 fix pass, as opposed to a direct `/release X.Y.Z` invocation — do not proceed on a generic confirmation. This branch records current `HEAD`, which is very likely NOT the commit that historical version was actually released at, and the skill has no way to target anything but the recorded `HEAD`; check out (or otherwise identify) the correct historical commit first, then require the user to affirmatively acknowledge the SPECIFIC commit SHA and branch you are about to tag as correct for that historical version (not a generic "yes, cut the release") before proceeding — the same acknowledgment discipline the Local-only-tag, branch-mismatch, and divergent-target-tag cases use for their own ambiguity. A bare "yes" must not carry a release onto whatever `HEAD` happens to be.** The confirmation below displays the SHA, but nothing else stops you tagging the wrong commit.
- **Local-only tag** (found locally, not on origin): do not treat this as an ordinary re-sync, and do not fold it into the confirmation copy below. A tag can end up local-but-not-on-origin two ways that are indistinguishable from git state alone: (a) a prior run of this skill created it and was interrupted before Step 5's push, or (b) the tag existed on origin, was deliberately deleted (e.g. a botched release rollback), and this clone still retains it locally — Step 2 deliberately never fetches or mutates local tags (see its own rationale), so case (a)'s local-only tag survives untouched, but that same choice is what makes case (b) indistinguishable here. Case (a) is safe to push; case (b) would resurrect a release the operator intentionally removed. Run `git log -1 --format='%h %s' "vX.Y.Z"` and show the user that commit/subject **plus an explicit statement that this tag is absent from origin and may have been deliberately deleted there** — require the user to affirmatively acknowledge that specific ambiguity before proceeding; a generic "yes, cut the release" confirmation does not count. **Additionally record the tag's full peeled commit SHA with `git rev-parse "vX.Y.Z^{commit}"` (the full 40-char commit SHA, not the abbreviated `%h` shown to the user) — this exact value is what Step 6's TOCTOU re-verify compares against for the local-only case, full SHA to full SHA; this local read equals what Step 5's push lands on origin because pushing a tag moves no commit.** A local-only tag already points at a fixed historical commit, so — like the Existing-tag case and unlike the New-tag case — **do not compare it to `HEAD` and do not require a clean worktree**; the dirty-worktree stop condition belongs only to the New-tag branch, which records current `HEAD` as the tag target.


`--verify-tag` aborts the command instead of creating a release against a tag absent from origin — a defensive backstop on top of Step 5's own push, in case the tag disappeared or was never actually pushed. `--repo ORIGIN_REPO` (Step 2) ensures this release is created in the same repository the tag was just pushed to. This captures `gh release create`'s own exit code into `create_rc` before `rm -f` runs, cleans up unconditionally, then re-exits the call with `create_rc` — so the Bash tool call's own reported status is the create command's, not `rm -f`'s (a bare `; rm -f` would report only `rm -f`'s near-universal success, exactly the masking the exit-status rule above forbids). If `create_rc` (or the echoed `create_exit_code`) is nonzero, stop and report rather than treating cleanup's success as the release's.
- If Step 3.1 recorded that a release already exists (the retrofit/re-sync case), same temp-file-and-quoting treatment: run `mktemp` in its own Bash call, carry its printed literal path forward, **read that freshly-created empty path with the native file-read tool first** (to satisfy the write tool's existing-file precondition), then write `<body>` to that literal path via the native file-write tool above (no shell command, no `trap`), then run the edit command for whichever of the following two sub-cases applies, cleaning up in the same status-preserving sequence introduced above so the Bash call's own reported exit status is `gh release edit`'s, never `rm -f`'s:
  - **Ordinary re-sync** — this is the default, and covers a direct `/release X.Y.Z` invocation as well as an Audit Step A4 fix of a `missing-tag`/`missing-release`/`drifted` classification. Edit notes only; do **not** pass `--draft=false`/`--prerelease=false`. An ordinary re-sync must never silently promote a draft to published or a prerelease to a full release just because its notes are being brought into canonical shape — that would be exactly the kind of consequential, externally-visible state change nobody explicitly asked for that this skill's confirmation-gate discipline (Step 4) exists to prevent (see Step 3.1's own draft/prerelease acknowledgment requirement, which covers editing a draft's/prerelease's *notes*, not transitioning its state).
    ```
    gh release edit vX.Y.Z --repo ORIGIN_REPO --title '<title>' --notes-file '<temp-path>'; edit_rc=$?; rm -f '<temp-path>'; echo "edit_exit_code=$edit_rc"; exit $edit_rc
    ```
  - **Publish/promote transition — reached only via Audit Step A4's `drafted`/`prereleased` fix triage** (see Step A4 below for exactly how that per-version choice is tracked forward to here; this sub-case must never be reached from a direct `/release X.Y.Z` invocation, since Single-Version Mode run standalone has no such choice to carry). When the user, triaging a `drafted` or `prereleased` classification in Step A4, explicitly chose "publish this draft" or "promote this prerelease" (not "leave alone" — that routes through the ordinary re-sync sub-case above, even though the release being edited is still a draft/prerelease at that moment), pass the flag(s) the chosen transition requires on top of the same `--title`/`--notes-file` edit. Which of the three concrete forms below applies is fixed by the classification Step A2 recorded (its `drafted` bullet records `isPrerelease` alongside `isDraft`) together with the user's Step A4 choice — never guessed here:
    - **(a) Publish a draft that is *not* also a prerelease** (classified `drafted` with `isPrerelease` recorded `false`; user chose "publish this draft") → `--draft=false` only:
      ```
      gh release edit vX.Y.Z --repo ORIGIN_REPO --title '<title>' --notes-file '<temp-path>' --draft=false; edit_rc=$?; rm -f '<temp-path>'; echo "edit_exit_code=$edit_rc"; exit $edit_rc
      ```
    - **(b) Promote a prerelease that is *not* also a draft** (classified `prereleased`, i.e. `isDraft=false`/`isPrerelease=true`; user chose "promote this prerelease") → `--prerelease=false` only:
      ```
      gh release edit vX.Y.Z --repo ORIGIN_REPO --title '<title>' --notes-file '<temp-path>' --prerelease=false; edit_rc=$?; rm -f '<temp-path>'; echo "edit_exit_code=$edit_rc"; exit $edit_rc
      ```
    - **(c) Publish a draft that *is* also a prerelease** (classified `drafted` with `isPrerelease` also recorded `true` — Step A2's `drafted` bullet; user chose "publish this draft") → both flags together, since publishing a draft that is also a prerelease must not leave the prerelease flag set behind it:
      ```
      gh release edit vX.Y.Z --repo ORIGIN_REPO --title '<title>' --notes-file '<temp-path>' --draft=false --prerelease=false; edit_rc=$?; rm -f '<temp-path>'; echo "edit_exit_code=$edit_rc"; exit $edit_rc
      ```
    This sub-case requires its own explicit confirmation in Step 4 — Step A4's routing states every fix passes through Step 4, and for this sub-case that confirmation's copy must name the transition itself ("publishing this draft" / "promoting this prerelease") as an action the user is affirmatively agreeing to, not merely the notes-sync a generic "yes, cut the release" already covers elsewhere — the same acknowledgment-gate discipline this file already applies to the Local-only-tag and branch-mismatch cases in Step 4.

  Both sub-cases capture `gh release edit`'s own exit code into `edit_rc` before `rm -f` runs, clean up unconditionally, then re-exit the call with `edit_rc` — so the Bash tool call's own reported status is the edit command's, not `rm -f`'s. If `edit_rc` (or the echoed `edit_exit_code`) is nonzero, stop and report rather than treating cleanup's success as the release's. This makes the skill idempotent on body content and safe to re-run against an already-published release to bring it into the canonical shape.
- `<title>` (the short `<repo> vX.Y.Z — <highlight>` line) has no `--title-file` equivalent in `gh`; single-quote it instead of double-quoting (`--title '<title>'`), escaping any embedded single quote in the highlight text as `'\''`. `<repo>` and the version are structurally safe (Canonical Format: `<repo>` comes from `gh repo view --repo ORIGIN_REPO --json name`, restricted to GitHub's own naming charset; the version passed strict SemVer validation in Step 1) — the highlight is the only piece of `<title>` with no such guarantee, since it's a short, human-drafted one-liner that could itself echo CHANGELOG text. Escape it the same way regardless.

Report the final release URL to the user.

## Audit Mode

`/release audit` finds gaps and drift across the **whole** repo instead of fixing one named version — this is the workflow that manually found skein's own three-shapes drift and its missing `v0.5.1` release, folded into the skill instead of repeated by hand.

### Step A1: Gather the Three Inventories

Resolve `ORIGIN_REPO` exactly as Step 2 does (host-qualified `HOST/OWNER/REPO` from the push URL, push/fetch-URL agreement checked, charset-validated per Step 2's items 1–2; sanity-check with `gh repo view --repo ORIGIN_REPO`) before running any `gh` command below, and pass `--repo ORIGIN_REPO` to each — Audit Mode runs standalone and does not inherit Step 2's resolution from Single-Version Mode.

1. **Tags**: Audit Mode is read-only (Usage, above) and must not mutate local refs to produce its report — **do not** run a forced tag fetch here: Step 2's pre-confirmation path no longer fetches local tags at all (see Step 2's own rationale) — a force-fetch would silently overwrite any local tag that has diverged from origin (a locally created test tag, or exactly the local-only-tag-recovery case Step 2/Step 4 exist to protect), and doing that as a side effect of a read-only audit is itself an unannounced mutation. Instead gather two non-mutating tag-name sets: **origin-authoritative** via `git ls-remote --tags origin` (strip each `refs/tags/` prefix and any trailing `^{}` dereference marker — same shape as Step 2's origin `ls-remote` read, its PREV candidate source), and **local** via a plain `git tag --list --sort=v:refname` with no preceding fetch. Origin's set is what actually decides tag existence (T) for classification (Step A2) — it reflects live remote state regardless of whether this clone has fetched recently, so staleness in the local list never produces a false `missing-tag`. A version present in the local set but absent from the origin set is not proof of anything wrong by itself; it is exactly the informational local-only-tag ambiguity the note below (Step A2's opening paragraph) already covers, resolved (if selected for a fix) through Step 4's own gate — never resolved here by silently rewriting the local ref. Apply Step 2 item 5's failure-handling rule to the `git ls-remote` call: a transport/auth failure must stop the audit, never be read as "origin has no tags." This inventory is intentionally **not** filtered to `v*`/strict-SemVer the way Step 2's PREV list is — Audit Mode's job is to surface non-standard tags as findings (`untracked-tag`), not silently discard them; step 4 below is where a non-semver tag actually gets excluded from *classification* (as opposed to being dropped from the inventory entirely).
2. **CHANGELOG versions**: every `## [X.Y.Z] - date` header in `CHANGELOG.md`, in file order (skip `## [Unreleased]`) — **use the same whitespace/punctuation-tolerant matching Step 1 item 5 uses** (extra spaces, en dash vs. hyphen), not an exact-string match. A CHANGELOG section is hand-edited content and can carry the same minor drift Step 1 already tolerates when resolving a single target version; inventorying with a stricter exact match here would silently drop a real, driftedly-formatted section from the CHANGELOG inventory, misclassifying an otherwise-fixable `drifted` release as `no-changelog-entry` (T=R=✓, C=✗ instead of the correct T=R=C=✓ row) and permanently hiding it from the punch list's fixable set.
3. **Releases (list only)**: `gh release list --repo ORIGIN_REPO --json tagName,name --limit 1000`. **Check whether the returned entry count equals the requested `--limit`** — that is the signal a single-page result may be truncated (this command returns at most `--limit` entries with no separate "more available" flag). If it does, do not silently classify against a possibly-incomplete inventory: re-run with a substantially higher `--limit` (or paginate via repeated calls with an increasing window) until a run returns fewer entries than requested, confirming the inventory is complete, before proceeding to Step A2 — an incomplete release inventory silently misclassifies real, older releases as `missing-release`, and selecting one in Step A4 would then attempt to re-create a release that already exists. `gh release list --json` does **not** support a `body` field — this call only tells you *which* tags have a release, not their content. Full name/body **and the `isDraft`/`isPrerelease` flags** for drift-checking and for the `drafted`/`prereleased` classification are fetched per-candidate in Step A2, not here (that per-candidate call uses `--json name,body,isDraft,isPrerelease`, matching Step 3.1's field names — `title` is never a valid `--json` field). This list call is **not** authoritative for `isDraft`/`isPrerelease`: because an audit over many versions can take real wall-clock time between this single list call and each later per-candidate call, Step A2's `drafted`/`prereleased`/`ok`/`drifted` classification reads those two flags from its own fresh per-candidate `gh release view`, never from this list snapshot — which is why they are not requested here at all.
4. **Normalize before unioning**: for tag names and release `tagName` values, strip the leading `v` **only if one is actually present** — a tag/`tagName` with no leading `v` at all (e.g. a bare `1.2.3`) is not this skill's release-tag shape and must not be admitted into the union as if it were; route it straight to the `non-release tag, ignored` reporting path below instead of stripping nothing and letting it pass through as a false SemVer match. For entries that do have the `v` prefix, strip it so every inventory keys on the bare semantic version `X.Y.Z` — CHANGELOG headers already use this bare form. Retain the `v`-prefixed spelling only when actually running git/gh commands (tag names, `gh release view`/`create`/`edit` targets). Unioning on the raw strings instead (`v0.5.1` vs `0.5.1` treated as different versions) splits every real release into a false `missing-tag` row plus a false `untracked-tag`/`no-changelog-entry` row. After stripping, **validate each stripped tag/release entry against strict SemVer** (`^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` — no leading zeros in any component) before adding it to the union — a malformed or prerelease-shaped tag (`v1.2`, `vfoo`, `v1.2.3-beta`, `v01.2.3`) does not satisfy the release-version contract this skill operates on. **Apply the same strict-SemVer validation to the CHANGELOG-header-derived version strings from A1.2, before they enter the classification union** — a malformed header (e.g. `## [1.2] - date`, missing the patch component) must be excluded and reported the same way malformed tags are, not admitted as a spurious `missing-tag` row for a non-existent/malformed version. CHANGELOG headers already use the bare `X.Y.Z` form (no `v` prefix to strip), so the SemVer gate applies to them directly. Entries that fail validation, or never had the `v` prefix to begin with, are excluded from the classification union in Step A2 and reported separately in the punch list as `non-release tag, ignored` (same informational treatment as `untracked-tag` — never silently coerced into a classification row or fed into PREV/compare-link computation).

**Platform invariant**: a GitHub release cannot exist without its underlying tag, so `release∃ ⇒ tag∃` always holds **on GitHub**. Because Step A1.1's tag-existence signal (T) is origin-authoritative (`git ls-remote --tags origin`, not a locally-fetched list), this invariant holds structurally regardless of this clone's local fetch state — there is no `release∃, tag∄` case to guard against separately.

### Step A2: Classify Every Version

A tag present in the local inventory (A1.1) but absent from origin carries the same ambiguity Step 4 flags (leftover interrupted run vs. a deliberately deleted release) — any classification built on such a tag (`ok`, `drifted`, `missing-release`) inherits that ambiguity. This is not resolved here: Step A4's fix pass runs Single-Version Mode against selected versions, and Step 4's gate there is what actually surfaces the warning and blocks an unacknowledged push back to origin.

Union the version strings from all three inventories (a version present in only one or two counts too — that asymmetry is the finding). For each version, classify by three yes/no facts — tag exists (T), release exists (R, only possible when T), CHANGELOG section exists (C):

| T | R | C | Status |
|---|---|---|---|
| ✓ | ✓ | ✓ | `ok` or `drifted` (see below) |
| ✓ | ✓ | ✗ | `no-changelog-entry` |
| ✓ | ✗ | ✓ | `missing-release` |
| ✓ | ✗ | ✗ | `untracked-tag` |
| ✗ | — | ✓ | `missing-tag` |

- **`drafted`** (T=R=C=✓, checked *before* `ok`/`drifted` below): run the per-candidate `gh release view vX.Y.Z --repo ORIGIN_REPO --json name,body,isDraft,isPrerelease` call as the **first action** for this candidate — this is the single fetch the `ok`/`drifted` bullet below reuses, and its freshly-fetched `isDraft`/`isPrerelease`, not Step A1.3's list-level snapshot, are authoritative for all three of `drafted`/`prereleased`/`ok`-vs-`drifted` (if this fetch fails, stop and report per the `ok`/`drifted` bullet's own failure rule below — a fetch failure means the classification is unknown, not a `drifted`). If that fetch's `isDraft` is `true`, classify it `drafted` and stop there — do not run the `ok`/`drifted` comparison and never silently edit or publish a draft. **Also record that same fetch's `isPrerelease` value alongside the `drafted` classification** — a release can be both (`gh release create --draft --prerelease`) — and surface both facts in the punch list (e.g. `drafted (also prerelease)`) rather than only `drafted`: this matters because if the user later chooses "publish this draft" in Step A4, that choice must also clear the prerelease flag when it was set, not just the draft flag (see Step 6's publish/promote sub-case). Surface it in the punch list and let the user decide (publish it, edit it, or leave it as a draft); Single-Version Mode's `gh release edit` is not draft-aware and editing a draft's notes is a different action than syncing a published release.
- **`prereleased`** (T=R=C=✓, `isDraft=false`, checked *before* `ok`/`drifted` below): using that same per-candidate fetch's freshly-fetched values (the `drafted` bullet above already ran the fetch), if `isDraft` is `false` but `isPrerelease` is `true`, classify it `prereleased` and stop there — do not run the `ok`/`drifted` comparison and never silently treat a prerelease as the stable release. Surface it in the punch list and let the user decide (promote it to a full release, edit it as a prerelease, or leave it alone); Single-Version Mode's `gh release edit` never passes `--prerelease`, so running it against a prerelease would silently sync notes onto a release the classification never flagged as non-stable, without ever promoting or demoting it.
- **`ok` vs. `drifted`** (T=R=C=✓, `isDraft=false`, `isPrerelease=false` only, all three judged from the fresh per-candidate fetch, not Step A1.3's list snapshot): for each such version, use the same per-candidate `gh release view vX.Y.Z --repo ORIGIN_REPO --json name,body,isDraft,isPrerelease` call the `drafted`/`prereleased` pre-checks above already ran as their first action (one call per candidate for classification purposes, its `isDraft`/`isPrerelease` authoritative over the list-level snapshot — `name` is the correct field, not `title` — see Step 3.1; Step A4 below does **not** reuse this fetch when actually applying a fix, since enough time can pass between classification and fix that the data goes stale) and extract that version's CHANGELOG section using Step 1's own extraction+tolerant-matching logic. If this `gh release view` call fails for any reason, stop and report the exact error for that candidate rather than folding the failure into `drifted` — a fetch failure means the classification is unknown, not that drift was detected. Split the fetched body into its `## What's New` paragraph (if any, via Step 3.1's recovery logic) and its remaining CHANGELOG-derived content. Classify **`ok`** only if `name` matches `<repo> vX.Y.Z — <highlight>` (any highlight text — audit doesn't judge highlight quality) AND the body's non-`What's New` content matches the freshly-extracted CHANGELOG section AND the trailing compare line is exactly right for this version's PREV: present, host-qualified to ORIGIN_REPO's own host (not a literal `github.com` — a GHE release's compare link must point at its own host), pointing at the correct PREV when a PREV tag exists — resolved by an **Audit-specific PREV calculation sourced from Step A1.1's already-gathered origin-authoritative tag set** (`git ls-remote --tags origin`), applying the same rule Single-Version Mode's Step 2 uses (keep only names matching strict SemVer `^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` after stripping `refs/tags/`/`^{}`, exclude this candidate version's own `vX.Y.Z` tag, sort by semver, PREV = highest tag below the target). Reuse the origin set A1.1 already captured — do **not** re-run `git ls-remote` here — and **never fall back to A1.1's local `git tag --list` set for PREV**: the local set stays reserved for the local-only-tag informational reporting described in this step's opening paragraph, exactly as Single-Version Mode now derives PREV from origin rather than local tags, so a stale or shallow local clone can never make Audit treat a release as first-ever (no PREV) or report a compare-link drift that isn't real — and with its `vNEW` segment (the right-hand side of the `...` in the compare link) equal to `vX.Y.Z` — a hand-edited link like `.../compare/v0.4.0...v0.5.0` with the correct PREV but the wrong `vNEW` is genuinely drifted, not `ok` — or **absent entirely** when no PREV tag exists (a stray compare line on a first release is itself drift, not a pass). Otherwise **`drifted`**, and name which check failed in the punch-list Note column — a title-only check is not sufficient; the CHANGELOG content and compare-link checks are what actually catch drift (skein's own pre-retrofit `v0.5.0`/`v0.4.x`/`v0.2.x` releases had correct-looking titles in some cases but stale/missing bodies).
- **`missing-tag`** — a CHANGELOG section exists but no tag does. (Skein's own `v0.5.1` before this session's first fix.) Fixable via Single-Version Mode — **but the fix routes through Step 4's New-tag case, which tags current `HEAD`. For an *older* missing-tag version surfaced by this repo-wide audit, `HEAD` is very likely NOT the commit that version was released at; the operator must check out (or otherwise identify) the correct historical commit before running the fix, since the skill has no way to target anything but the recorded `HEAD`.**
- **`missing-release`** — a tag and a CHANGELOG section both exist, but no release does. Fixable via Single-Version Mode.
- **`untracked-tag`** — a tag exists with **neither** a release nor a CHANGELOG section (e.g. an old experimental or pre-adoption tag with no recorded notes at all). **Not** fixable via Single-Version Mode — Step 1 there requires a CHANGELOG section to resolve and will dead-end. Informational only, same as `no-changelog-entry`: report and move on, never invent changelog content to make it fixable.
- **`no-changelog-entry`** — a tag and release both exist but no CHANGELOG section does (common for pre-CHANGELOG-adoption tags). Informational only — do not propose "fixing" these by inventing changelog content; report and move on.

### Step A3: Report the Punch List

```
## Release Audit: <repo>

| Version | Status | Note |
|---|---|---|
| v0.5.1 | ok | — |
| v0.5.0 | drifted | title missing highlight; body still has CHANGELOG header embedded |
| v0.2.0 | no-changelog-entry | tag+release predate CHANGELOG.md |
| v1.2 | non-release tag, ignored | tag doesn't match strict SemVer, excluded from classification |

N ok, M missing-tag, K missing-release, U untracked-tag, D drifted, W drafted, P prereleased, C no-changelog-entry, X non-release tag ignored
```

Do not mutate anything in this step — Audit Mode is read-only by itself.

### Step A4: Fix (Opt-In, One Version at a Time)

After the report, ask the user which **fixable** versions to fix (`missing-tag`, `missing-release`, `drifted` only — never `untracked-tag`/`no-changelog-entry`, and never silently include `drafted` or `prereleased`: ask separately whether a draft should be published, edited, or left alone, or whether a prerelease should be promoted to a full release, edited as a prerelease, or left alone, before running Single-Version Mode against either) — a free-form selection (`all`, `1,3`, `none`), the same pattern `skein:review-plan`'s Step 6.4 triage uses for an unbounded finding list rather than a capped multiple-choice widget. For each selected version, run **Single-Version Mode** (Steps 1–6 above) against it, including its own Step 4 confirmation — Audit Mode's own confirmation (choosing which versions to fix) does not substitute for each fix's own mutation-confirmation gate. **For a `drafted`/`prereleased` version specifically, "run Single-Version Mode" is not enough on its own — record the user's publish/promote/leave-alone choice *alongside* the selected version, not just the version number, and carry that pairing through every subsequent step**, since nothing else in Single-Version Mode persists it: the choice reaches Step 4 as the specific transition named in that step's confirmation copy ("publishing this draft" / "promoting this prerelease" for a publish/promote choice — see Step 6's publish/promote sub-case, which requires exactly this acknowledgment — or the ordinary re-sync confirmation for "leave alone"), and from there reaches Step 6 as which of its two edit sub-cases actually runs: a "publish this draft" or "promote this prerelease" choice must land on Step 6's publish/promote sub-case (the extra `--draft=false`/`--prerelease=false` flag), while a "leave alone" choice (edit notes only, don't transition) must land on Step 6's ordinary re-sync sub-case — no `--draft=false`/`--prerelease=false` — even though the release being edited is still, at that moment, a draft or a prerelease. If only the version list is carried forward and the per-version choice is dropped or re-inferred, Step 6 has no reliable way to tell "leave alone" from "publish," so the choice must travel with its version through Step 4 into Step 6, never be re-asked or re-derived at Step 6 time. **For a `missing-tag` version specifically, that Step 4 confirmation routes through the New-tag case, which records and tags current `HEAD` — and because an *older* audit-surfaced `missing-tag` version was almost certainly released at some commit other than `HEAD`, Step 4's New-tag case there requires the user to affirmatively acknowledge the specific commit SHA and branch being tagged as correct for that historical version (not a generic "yes"); check out (or otherwise identify) the correct historical commit before running the fix, since the skill can target nothing but the recorded `HEAD`.** **For a `drifted` version, let Step 3.1 make its own fresh `gh release view` call rather than reusing A2's `name`/`body` fetch** — the report (Step A3) and the user's fix selection here are separated by an unbounded human review gap, during which the release can genuinely change (another operator edits it, a CI job republishes it); treating A2's classification-time snapshot as still current when actually mutating would risk acting on stale data with no re-check, the same class of staleness risk a mutation-adjacent read must never carry. `missing-tag`/`missing-release` versions already require their own Step 3.1 call regardless (A2 never fetches full release content for T=✗/R=✗ candidates). Process one version at a time, in ascending version order, so an interrupted batch leaves a clean prefix of fixed releases rather than a scattered partial state.

**Fixing a `missing-tag` can stale an adjacent, unselected release.** Inserting a new tag between two existing versions changes what PREV resolves to for the release immediately above the newly-inserted one (Step 2 computes PREV fresh from the current tag list every run) — but that adjacent release was already `ok` and wasn't selected for fixing, so its now-stale compare link goes unnoticed. If this batch fixed any `missing-tag` version, tell the user to re-run `/release audit` afterward rather than treating the batch as having left the repo fully clean.

## Execution Model

Unlike `rfc-finder`/`update-docs` (read-only, subagent-delegated fact-gathering), this skill runs entirely **inline in the main agent context** — no delegating subagent. It owns an irreversible external mutation (tag push, release publish) gated on an explicit user-confirmation step (Step 4); a subagent cannot hold that confirmation gate on the caller's behalf.

It also has one **data-contract** dependency worth naming, distinct from a call-chaining edge: it parses the exact Keep a Changelog `## [X.Y.Z] - date` shape that `skein:update-docs` produces/maintains in `CHANGELOG.md`. If either skill's format assumption drifts, this skill silently mis-parses (empty body, wrong header strip). No skill calls another here — the two only share a format contract.

## Edge Cases

- **No `CHANGELOG.md`**: stop and tell the user — this skill has no fallback source for release notes.
- **Version argument doesn't match any CHANGELOG section**: stop and report the mismatch; do not guess the nearest version.
- **`gh` not installed or not authenticated**: stop and tell the user to authenticate (`gh auth login`) before retrying.
- **Target version's tag exists but points at an unexpected commit**: flag this to the user before reusing it — do not silently move or re-tag.
- **`gh release view` fails for a reason other than "release not found"** (network error, repo-resolution failure, insufficient permissions): stop and report the exact error (Step 3.1) — never fall through to `gh release create` on an ambiguous failure.
- **Tag exists locally but was never pushed to origin**: treated as ambiguous, not an ordinary re-sync (Step 4) — the operator must explicitly acknowledge that the tag may have been deliberately deleted from origin before Step 5 pushes it; `gh release create --verify-tag` is a second, defensive check in case that push didn't actually land.
- **Release cut from a non-default branch**: Step 4's New-tag case compares the recorded branch against Step 2 item 4's cached `defaultBranchRef.name` and requires an explicit acknowledgment before proceeding when they differ (skipped entirely when `defaultBranchRef` is `null`).
- **Local tag diverged from origin's tag for the same version**: Step 4's Existing-tag-on-origin case surfaces both commits and requires an explicit acknowledgment before proceeding.
- **Existing release is a draft or prerelease when Single-Version Mode targets it directly**: Step 3.1 surfaces this in Step 4's confirmation and requires an explicit acknowledgment before `gh release edit` runs, since Single-Version Mode's edit is neither draft- nor prerelease-aware by default.
